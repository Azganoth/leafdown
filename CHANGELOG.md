# Changelog

All notable user-facing changes to Leafdown are documented in this file.

Leafdown uses lightweight [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) sections and version names that match the application package version.

## [Unreleased]

### Added

- Open a Markdown file or folder by dropping it anywhere on the Leafdown window, with the same unsaved-change handling, pinned folder context, index-file behavior, and recent-item recording as the File menu. A window-wide overlay previews the configured action while the item is dragged over Leafdown, or explains why the drop is unavailable. Two persisted Files preferences can instead insert a link into the active document: saved documents receive a relative link when possible, while untitled documents receive an absolute one. Multi-item and unsupported drops are left alone with a warning.
- Choose a Neutral, Red, Orange, Amber, Emerald, Cyan, Blue, Violet, or Fuchsia accent color from a previewed menu in Preferences. Neutral preserves Leafdown's original monochrome primary treatment; every choice carries links, editor selection and caret treatment, checked task checkboxes, quote bars, list glyphs, selection rings, active article rows, and filled primary controls in both appearances, and stays after restarting Leafdown.
- Add a paragraph at the end of the document by clicking the empty space below it.
- Close folder contexts from the File menu.
- Add keyboard shortcuts for formatting task lists and toggling task items.
- Go from a footnote reference to the footnote it names, with `Mod+click` on the reference or `Jump to footnote definition` in the Edit menu, instead of hunting for the definition further down the file. Every reference sharing a label reaches the same definition, the caret lands in the definition's own text, and the plain click still opens the reference's source as before. Nothing about the file changes: the Markdown, the unsaved marker, and what `Undo` steps back to are the same after the jump as before it. A reference whose definition has been deleted, or one relabelled to a name no definition answers to, goes nowhere and greys the command out.
- Read a footnote without leaving the line it is cited on. Resting the pointer on a reference shows what the definition says after a short pause, and `Mod+Alt+P` shows the same thing for the reference the caret is on, so the preview is reachable without a mouse. It is a preview and nothing more: it holds no buttons, never takes the caret, and shows the definition on one line, cut short where the footnote is longer than fits. A reference whose definition is gone says so instead of showing an empty box. Moving the pointer away, `Escape`, or carrying on typing puts it away, and the file is untouched throughout.
- Restore every setting to its default from the preferences dialog.
- See when each recent file and folder was last opened, beside it on the welcome screen, so a file opened this morning no longer looks the same as one opened months ago. Reopening an item updates its time. Recent items kept from before this change stay in their order and show no time until they are opened again.
- Remove a single recent file or folder from the welcome screen, instead of clearing both lists to be rid of one entry. A recent item that was moved or deleted no longer has to keep answering with an error until everything else goes with it. The other entries in both lists stay where they were, and `Clear recent items` still clears both.

### Changed

- Rebuild the welcome screen as a launcher. `New document` joins `Open file` and `Open folder`, so the fastest way to start writing is no longer the least visible one, and each of the three names its keyboard shortcut the way the menus do. A recent item is listed by its own name with the folder holding it beside it, where the row used to be the full path cut off at the end, which is where the file name is. The recent lists stay away entirely until there is a recent item to list. `Clear recent items` is a small action under the lists it clears instead of a full-size button in the row beside `Open file`.
- Show the article navigator only while a folder context is open. Without one it had nothing to list and stood beside the welcome screen repeating what that screen already said, so the document surface now spans the workspace instead. `Toggle sidebar` is unavailable until a folder opens, in the View menu and in the titlebar alike, and leaves the sidebar visibility setting as it found it, so a sidebar hidden before one folder closed is still hidden when the next one opens.
- Refine how the editor draws blocks. A block quote's accent bar is half its former width. A task list checkbox stands as an unfilled outline with a stronger edge until it is checked, then carries the same filled box and tick as the checkboxes elsewhere in the interface, and a checked item's own text is muted. Table cells are separated by single rules that stop at the table's own edge rather than boxing each cell, cells have more room around their text, and rows no longer alternate their shading. A fenced block's language sits in a badge in the block's corner instead of floating as bare text, and the block itself no longer carries an inner shadow. The badge beside a heading that names its level is filled and lettered like one too, where it was an outline holding the page's own colour.
- Hold a table's columns still while the caret works inside it. A column takes the width of what it holds, so putting the caret in a cell moved it: the cell shows its Markdown source, markers and all, which made it wider and pushed every column beside it along, and leaving the cell moved them all back. The columns are settled before the caret arrives and held while it is inside, so a cell's source opens into room already reserved. A table fits its columns again once the caret leaves it and whenever the editor changes width, so a column still follows what the table holds.
- Line a list's markers up in a column of their own. A bullet, a checkbox, and a number now all begin at the same place, the edge the paragraphs around the list start from, and the item's text begins one column in. A number is set against its dot rather than its first digit, so the dots hold a column of their own and a list that reaches `10.` keeps every one of its items' text where the others are, the longer number reaching to the left instead. A nested item's marker begins exactly where the text of the item holding it begins, one column for each level, instead of standing a further step to the right of it. The gap between an item and the one nested under it is now the gap between any two items, so indenting with `Tab` and unindenting with `Shift+Tab` move an item sideways without moving anything below it.
- Hold a heading still when its marker appears, and show that marker on hover as well as to the caret. The marker now stands in a column reserved next to the document instead of in the heading's own line, so the heading no longer slides sideways as the caret enters and back as it leaves, and a heading long enough to wrap no longer reshuffles its lines. Resting the pointer on a heading shows the same marker, so a heading's level can be read without putting the caret in it; the marker is part of what the pointer is resting on, so reaching for it does not make it vanish. The column is held open whether or not a marker is showing, at every window width; where the window is too narrow to hold both it and the text at full width, the text narrows rather than the marker crowding it.
- Bind a heading to the text it introduces. The paragraph or list directly beneath a heading now sits closer to it than the heading sits to whatever came before it, so a section reads as one block rather than as evenly spaced lines. A block quote, code block, table, image, or separator beneath a heading keeps its own spacing, since each already carries its own frame.
- Space a heading according to its level instead of giving every level the same gap. A first-level heading now takes the most room above it and a fifth- or sixth-level heading the least, just clear of ordinary paragraph spacing, so a glance down a document reads its structure from the spacing as well as the type size. A heading standing directly under another sits close to it, because it introduces that heading rather than following prose.
- Set the top two heading levels apart by their size alone, instead of drawing a rule under them as well. Only first- and second-level headings carried that rule, so the two levels the type scale already separates furthest were the only ones marked a second time. Both also lose the padding that held their text clear of the rule; the space a heading keeps above the text it introduces is unchanged.
- Draw a selected block's outline in the interface's own colour rather than the editor library's fixed blue, so selecting a separator, an image, a code block, or a list item reads as part of Leafdown in either theme.
- Draw a separator as a short centred rule instead of a line across the text. A full-width line was the same mark as the underline first- and second-level headings used to carry, so the two could not be told apart; the separator still spans the text where it can be clicked, and only the mark it draws is shorter.
- Darken the dots on the divider between the article navigator and the document while the pointer is over it, so the divider reads as something to drag before it is dragged.
- Show an open folder beside an expanded folder in the article navigator, so a folder's icon says what its arrow says.
- Reduce the article navigator's header to its name and a badge counting the articles it lists.
- Integrate the command menu into the titlebar, replace the app-name label there with the Leafdown icon, provide a persistent sidebar toggle beside the native window controls, present the article navigator and document editor as aligned cards, resize the article navigator by dragging the divider between the two, hold the document card in place while its text scrolls so its scrollbar runs inside the card rather than down the side of the window, add article filtering, and soften the default dark-theme text color across the editor and interface.
- Rebuild the preferences dialog around a rail of sections down its side — General, Files, Editor, and Appearance, the grouping the settings documentation already uses. Every preference is a row carrying its control, where switches stood in rows and choices stood as stacked blocks below them, and a choice's options are one segmented control instead of a grid that left a hole beside two-option settings. The panel holds one height, so moving between sections no longer resizes the dialog under the pointer, and the switch for the final newline stands apart from the line-ending choices rather than reading as one of them. The footer carries only the dialog's own actions now, since the corner already closes it.
- Rebuild the About dialog around what the app is: the Leafdown mark, the name, and the version of the build that is running, above the links it already offered. It reported the license in a sentence and nothing else, and which build was running could only be read from the diagnostics dialog.
- Lead the diagnostics dialog with the facts it reports — the application and its version, its identifier, the platform, and the current run — where it opened on a box of text to copy with two of those lines repeated beneath it. The summary is still there behind `Show summary`, because the clipboard can be unavailable and the text is worth reading before it is pasted into a report. What logs may contain now reads as the caution it is rather than as the dialog's subtitle.
- Tighten the padding on the icon side of buttons that carry a leading icon, such as `Open file` on the welcome screen and `Copy summary` in the diagnostics dialog, so the icon no longer sits as far from the edge as the text does on the other side.
- Sort article directories before articles in the article navigator.
- Ease the editor context popup between selection-driven positions while keeping scroll tracking immediate.
- Separate global application shortcuts, focused editor command shortcuts, and native text-input and clipboard gestures by ownership.
- Extend seamless in-document Markdown source projection to strikethrough, inline code, links, autolinks, and footnote references.
- Present active mixed-format link labels as one coordinated source range.
- Extend link label source projection to labels that contain an image, such as badge links.
- Keep a URL written on its own as it was written, bare or between angle brackets, instead of putting angle brackets around every bare URL in the file on the first save.
- Turn a typed link, URL, or angle-bracket URL into the link it describes once the caret leaves it, as pasting the same text already did.
- Show the backslash that keeps link or image text literal when the caret reaches it, so deleting the backslash turns the text into the link or image it describes.
- Turn typed image text into the image it describes once the caret leaves it, as typed link text already did.
- Show a character reference such as `&copy;`, `&#169;`, or `&#xA9;` as it was written when the caret reaches it, so it can be told apart from the character it names and removing any of its characters turns it into ordinary text.
- Write a list or heading made in the editor in the form the rest of the document is written in, so a list added to a file whose lists are all `-` is written `-` rather than `*`, an ordered list added to a file written with `)` keeps `)`, and a heading added to a file of underlined headings is underlined too, at the width of its own text. A heading added to a file whose headings all close with hashes closes with them, at its own level, and one written after a tab is written after a tab. Where a file disagrees with itself about any of these, or says nothing about them, the editor's own `*`, `.`, and `#` are written as before, and a construct keeps the form it was made with even if the file stops agreeing later.
- Turn a typed character reference into the reference it spells as its closing `;` lands, so `&copy;`, `&#169;`, and `&#xA9;` can be written as well as broken and a reference removed by accident can be put back without editing the file elsewhere. Nothing moves on screen: the characters stay where they were typed, the caret stays after the `;`, and the run restyling to the muted syntax colour is what says it happened. One `Undo` gives back the run as it was typed. An unclosed or made-up reference such as `&copy` or `&MadeUpEntity;` is left alone, as is a run that crosses bold or italic, one inside a code span, and one typed after a reference the file already holds, so typing `copy;` after `&amp;` still saves `&amp;copy;`. Typing the characters now reaches the same document as pasting them.
- Show the character a character reference names beside its source while the caret is on it, so `&copy;` reads as `©&copy;` rather than hiding the answer the source was opened for, and a reference naming a no-break space or nothing visible can be told from one naming a letter. The character reads as the text it renders while the source beside it is muted like the rest of the syntax, and the pair moves as one under the caret. The character is shown wherever a reference is projected, including inside bold, italic, or strikethrough and inside a link label, and it is drawn beside the source rather than written into it, so nothing reaches the file, a copy, or the positions the caret moves through.

- Show both neighbours when the caret sits between two of them, instead of opening one and leaving the other rendered. A caret between a link and italic text, between two links, or between two character references now reads both as the file will write them, keeps its place between the two, and reads the same whether it arrives by click or by arrow key and from either side. The place where the two meet belongs to neither: a character typed there becomes text between them and both survive it, `Backspace` takes from the source before it and `Delete` from the source after it. Moving the caret into one of the two leaves that one open and puts the other back, so only what the caret is on reads as source. Editing one commits that one and leaves its neighbour exactly as the file held it, and leaving both alone restores both. A caret between two references inside a link label still opens the link, and an escaped run beside another object still turns into what it describes as soon as its backslash goes.

- Rename a footnote by typing its label. A footnote definition now shows its source the way the file holds it — `[^`, the label, and `]:` as separate runs with the label in bold between them — and the label is ordinary text a caret reaches and edits, so renaming a footnote no longer means deleting the line and writing a new one. Every reference that named the old label is renamed with it, so nothing is left pointing at a label the file no longer defines. The label takes effect when the caret leaves it, and saving while the caret is still in it saves the label typed. A label left empty, holding a bracket or a line break, or already used by another definition is not taken, and the definition keeps the label it had. `Undo` puts the earlier label back and returns the caret to it, so the rename is undone when the caret next leaves or the file is saved. Editing a reference's own label still renames nothing.

### Fixed

- Keep a character reference in a link or image title, a definition's title, or an image description as it was written, such as the `&copy;` in `[l](d.md "t &copy;")` or `![a &copy;](d.png)`. Saving wrote it as the character it names, so a file kept to plain ASCII did not stay that way. Once the title is edited, the reference is saved as its character, the same as anywhere else. An image description edited through the image's Markdown now reads a reference typed there as the character it names, the way the file does, where it used to keep the reference's characters as literal text. A definition title holding an escaped reference, such as `\&copy;`, lost its backslash on save and reopened as `©`; it is now saved as written.

- Keep a character reference on a line that ends in a space or a tab, such as `&#x20;` in `&#x20;a ` followed by a second line, as it was written. Saving wrote every reference on such a line as the character it names, so a space a reference named at the start of a paragraph or list item was gone once the file reopened. The reference is now written back as it was; the space or tab ending the line is still left out.
- Keep a web address starting with `www.` bare when the character written just before it is not a space, such as the quote in `"www.example.com"`, a `;`, or a character reference like `&#x20;` or `&nbsp;`. Saving wrote the address as a full link, `[www.example.com](http://www.example.com)`, and wrote a reference before it as the character it names. Where that reference opened a paragraph, a heading, or a table cell, the space it named was gone once the file reopened. The reference is now written back as it was, and so is the address, unless it is followed by a character such as the `>` in `<www.example.com>`, where it is still written as a full link.
- Read a code span pasted as plain text into a table cell the way the saved file reads it. Pasting `` `a \| b` `` into a cell, on its own or inside a link's text, kept the backslash as part of the code, so the cell showed `a \| b` until the file was saved and reopened as `a | b`. The code now holds `a | b` as soon as it is pasted, as it does when the same characters are typed. Pasting the same text outside a table keeps the backslash, as the file does there.
- Read a code span typed into a table cell the way the saved file reads it. Typing `` `a \| b` `` in a cell kept the backslash as part of the code, and saving wrote it as `\\|`, which ended the cell when the file was reopened: the row split inside the code, and the row's last cell was dropped. The code now holds `a | b` and is saved as `` `a \| b` ``, as it would be read from the file. Code that really holds a backslash directly before a `|`, such as code pasted or moved into a cell, has no spelling a table cell reads back; it is now saved without the escape that split the row, and reopens without that backslash.
- Keep the backslash before a `|` in the label of a reference link or image, such as `[text][a\|b]` with its definition `[a\|b]: doc.md`. Saving wrote both labels with a bare `|`. In a table cell that ended the cell when the file was reopened: the row split inside the reference, the link or image was gone, and the row's last cell was dropped. Outside a table, two definitions whose labels differed only by that backslash were saved as one label, so the second one's links led to the first one's destination. Every label, in a reference and in its definition, is now written as the file spelled it, and a shortcut or collapsed reference keeps its form.
- Keep the backslash before a `|` in the destination or title of a link whose text mixes formatting when the link stands in a table cell. Saving wrote the bare `|`, which ended the cell when the file was reopened: the row split inside the link, the link was gone, and the row's last cell was dropped. The escape is now written back as it is for a link whose text has a single formatting or none.
- Show the backslash a table cell keeps before a `|` in the source the caret opens there. In a link, a bold, italic, or strikethrough run, or a code span whose text holds `\|`, the source showed a bare `|`, which is not what the file holds and not something a cell can hold, since a bare `|` ends the cell. The same went for a link spelled out as plain text and for two formatted runs meeting in a cell. The source now shows `\|` as the file holds it, and an edit made there is still saved with the backslash. The saved file was never affected.
- Keep the form a reference link was written in when its text mixes formatting. A shortcut reference such as `[**bold** text]`, or a collapsed one such as `[**bold** text][]`, was saved as the full reference `[**bold** text][**bold** text]`, spelling its text a second time. It still led to the same place, but the file no longer read as it was written. Both forms are now written back as authored, as they already were for text with a single formatting or none.
- Keep a link whose text mixes formatting and holds raw HTML, such as `[**bold** text<br>more](doc.md)`, as one link when saving. Such a link was written back as two, `**[bold](doc.md)**[ text<br>more](doc.md)`, one holding the formatted text and one holding the rest, so the first save split it. The raw HTML inside it is still written back as it was authored.
- Show a code span's source over the whole of what it holds when it starts or ends with a space. The caret showed no source until it was past that space, and then showed the backticks inside the spaces rather than around them, so `` `  code  ` `` read as a space on each side of `` `code` ``; a span holding only spaces showed no source at all. Such a span now shows the source the file holds from anywhere inside it. A space typed against either backtick of a span showing its source was deleted once the caret left, so `` `code` `` with a space typed onto each end came back as plain `code`; it is now kept as part of the span, which is written as `` `  code  ` ``.
- Keep the `Edit`, `Insert`, and `Format` menus in step with the caret. On a document just opened, every editor command in them was greyed out until the document was edited, and from then on they answered for wherever the caret stood at the last edit, so moving the caret into a table left `Table` greyed out and moving it out left the table commands available. The menus now offer what the context popup offers for the caret as it is, from the moment the editor is ready.
- Keep every character reference in a quote, list item, or footnote paragraph that runs onto a second line, such as `&#x20;`, `&#9;`, `&nbsp;`, or `&copy;`, as it was written. In such a paragraph a space or tab a reference names at the end of a line was gone as soon as the file opened, taking a space typed just before it too, so the first save wrote the line without them. A reference opening a later line was dropped on save, and every other reference was saved as the character it names. The paragraph now opens holding what the file spells and is saved as it was written, as the same lines outside a quote, list, or footnote already were. A space or tab typed at the end of such a line is still left out.
- Keep the backslashes inside the text of a link whose text mixes formatting. A backslash written there was saved as the bare character it held, which for a `]` closed the link early when the file was reopened: the link was gone and the whole construct read as plain text, and a `[` could turn into a second link the file never held. In a table cell the same loss took the cell's own `|`, splitting the row. Such text now keeps the backslash that holds a bracket or a cell's `|` literal, and a bracket the text spells without one is written with one, which is what the text of a link with a single formatting or none has always been written as.
- Keep the shape of the lines around a link whose text mixes formatting and runs onto a second line. Inside a quote, a list item, or a footnote, the link's later lines were written without the `>` or the indentation they were read with, and a heading holding such a link was saved in a form that reopened as a heading and a separate paragraph, leaving the link as plain text. Each line is now written under the prefix it was read with, and such a heading is saved the way a heading holding any other line break already is, so it reopens whole with the link intact.
- Size a table column and a heading's underline by the link they hold, where a link whose text mixes formatting made both as wide as an internal marker, padding a column to 31 characters no cell needed. A link's text holding `$&`, `$'`, or another replacement pattern is also written as the text it is, instead of putting that internal marker into the saved file.
- Keep the spaces at either end of a link's text inside its brackets when saving, so `[ label ](https://example.com)` is written back as it was instead of with its spaces moved outside the brackets, which reopened as a link over less text than the file gave it. The same applied to a reference link, and a shortcut reference such as `[ label ]` was rewritten in the longer `[label][ label ]` form. Where the link's text mixed formatting, as in `[ **bold** label ](https://example.com)`, the spaces were dropped instead. Such a link also showed no source while the caret was in its text, so its destination and title could not be reached; it now opens its whole source, spaces included, and an edit keeps them.
- Keep a space or tab written as a character reference, such as `&#x20;` or `&#9;`, as it was written, instead of saving the character it names. Where two of them met the end of a line, the file came back holding a line break the document never had; where one did, the file held a space the next open threw away, so a second save differed from the first. The reference is now written back wherever it stands — at either end of a line, in the middle of one, in a heading, list item, quote, or table cell, and inside bold, italic, or struck-through text — and the line ending, the hard break, and the formatting beside it are saved as the file held them. A space or tab typed at either end of a line is still left out, and `&nbsp;` keeps its source as it always did.
- Show the whole source of a link, or of bold, italic, or struck-through text, that breaks its line with a backslash or a run of spaces. Such a link showed no source at all while the caret was in its text, so its destination and title could not be reached, and such bold or italic text showed each line as a run of its own, with markers the file does not have closing the first line and opening the second. Both now open as one piece of source across the break, as they already did across an ordinary line ending, and the break shows the backslash or the spaces the file holds. A run of spaces at the end of a line is invisible, so each space in it is marked with a faint dot while the source is showing. An edit keeps the break as it was written.
- Keep a link whose text mixes formatting and breaks its line with a backslash or a run of spaces as one link when saving, wherever it stands other than in a heading. Such a link was written back as two, one holding the formatted text and one holding the rest, so the first save split it.
- Keep the links, footnote references, and character references inside bold, italic, or struck-through text that runs onto a second line when that text is edited through its source, including when the caret stands between that text and a link or reference right after it. The edit turned each of them into the literal text of its source, so a link inside the run was saved as bracketed text instead.
- Colour a code block's syntax for the theme in use. Every block was coloured from the dark syntax theme in both appearances, so in the light theme a block's plain text read as a bright grey and the rest of its colours were pitched for a background it did not have. A language Leafdown does not highlight reads as ordinary editor text now instead of taking that theme's colour for its own.
- Keep the gap between the document card and the left edge of the window when the sidebar is hidden. That gap was drawn by the article navigator standing beside the card, so collapsing the sidebar took it away and the card ran into the side of the window. The gap is now held by the surface the two cards sit on, so it is the same whether the sidebar is showing or not.
- Remove the empty column down the left of the rows in the editor context popup's `Block type` and `Insert` submenus. Every row there already carries its own icon, so the column a menu reserves for ticking its rows was standing empty and pushing each label a step to the right.
- Show the border around inline code in the light theme. It was drawn in a colour that only shows against a dark background, so a `code` span read as a plain grey block in light while the same span carried an edge in dark. Inline code showing its source under the caret is drawn the same way and carries the border again too.
- Line up the rows of the View menu. `Toggle sidebar` and `Full screen` reserve a column on their left for the tick that marks them on, and the rows sharing the menu with them did not, so `Zoom in`, `Appearance`, `Sort articles by`, `Collapse all folders`, and the rest began a step to the left of the two and the menu read as two ragged columns. Every row of the menu now begins at the same place, whether it can carry a tick or not. The submenus are unchanged: each one's rows already agreed with each other.
- Keep that whitespace on a heading underlined with `=` or `-` whose text runs across more than one line, so a line written without its `>` or its item's indentation stays that way and one written indented keeps its indentation, as a paragraph's already did. The underline keeps whatever it was written behind too.
- Keep the indentation a nested list item's marker was written behind, so an item indented by a tab under `- parent` stays indented by a tab instead of being rewritten as two spaces, and the lines the item holds move with it. An item the editor moves into or out of another item is still written at the indentation its containers spell, and so is one whose recorded indentation would put its marker inside the item before it.
- Keep the leading whitespace a paragraph's later lines were written with, so a quoted line written without its `>` no longer gains one on the first save, a list item's second line written without indentation no longer gains it, and a line indented inside a paragraph keeps that indentation instead of losing it and gaining a backslash in its place. A line added in the editor is still written under the marker or indentation its blockquote or list item spells, and so is one whose recorded whitespace would open a quote the document no longer holds.
- Keep two blocks written on consecutive lines together, so a paragraph followed straight away by `<section>`, a heading, a list, a quote, a fence, a table, or a `***` rule no longer gains a blank line between them on the first save, and neither do two headings, two reference definitions, or a paragraph written directly under a heading, rule, or code block. Blocks written with a blank line between them keep it, and a blank line is still written wherever taking it out would merge the two blocks into one — after a raw HTML block, before a line a reference definition would read as its title, and wherever an edit has left the second block unable to interrupt the first.
- Keep the form a heading was written in, so `# Level one #` keeps the hashes closing it instead of losing them on the first save, and a heading underlined with `=` or `-` stays underlined instead of being rewritten as `#`. The underline keeps the length it was written at, and the spaces or tabs between an opening `#` run and the heading text are kept too. A heading made in the editor is still written with `#` and nothing closing it, and so is one moved past the levels an underline can carry or written where the underline would be read as part of the paragraph above it.
- Keep that form when a formatting command changes a heading's level, so `Heading 1` through `Heading 6` leave a heading exactly as `Increase heading level` and `Decrease heading level` already did. A heading underlined with `=` stays underlined when `Heading 2` moves it, and `# Level one #` keeps the hash closing it when `Heading 3` moves it, instead of arriving as a rewritten heading a gesture before a save would have written one. A heading turned into a paragraph and made a heading again is a heading the editor made, and is written as one.
